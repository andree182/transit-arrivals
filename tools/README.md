# tools/ — station-data builders

Node scripts that generate the static station databases used by the phone JS (`src/pkjs/lib/*.stations.json`) and the worker's per-agency fanout/timetable files (`cta-proxy/src/agencies/*.json`). Each builder's header comment documents its data source and exact usage; the table below is the map.

## Shared libs (`tools/lib/`)

- `gtfs.js` — minimal GTFS CSV reader (`readDir` parses a directory of GTFS .txt files, handles quoted fields).
- `gtfs-rail.js` — `buildRailArtifacts(gtfs, cfg)`: filters a GTFS feed down to rail routes via a per-agency `labelFor`, merges same-named platform stops, and emits both the phone station DB and the worker's station→stop_id/route data.
- `gtfs-schedule.js` — `buildScheduleArtifacts(gtfs, cfg)`: builds on `gtfs-rail.js` to also compact the full timetable (stop_times + calendar) for schedule-only agencies (PATCO, Tren Urbano).

## Tests

Builders keep their transforms pure and unit-tested with Node's built-in runner:

```sh
node --test tools/*.test.js tools/lib/*.test.js
```

## Warning: NYC has no from-scratch builder

`src/pkjs/lib/stations.data.json` (the NYC subway + PATH database) is **not** regenerated by any script here. It is maintained by three one-off scripts applied **in this order**:

1. `merge-complexes.js` — merges same-complex stations using MTA GTFS `transfers.txt` (from `https://rrgtfsfeeds.s3.amazonaws.com/gtfs_subway.zip`).
2. `attach-path.js` — overlays PATH stations, merging co-located platforms into their subway entry.
3. `center-complexes.js` — recomputes each merged complex's pin as the centroid of its member platforms (run **last**).

All three rewrite `stations.data.json` in place; running them out of order (or rebuilding from scratch) loses the merged/attached state.
